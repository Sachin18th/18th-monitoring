## CHUNK 8 — Multi-Tenant Design (chunk_8.pdf, full document)

### BC. Tenant hierarchy model (verify in schema/relations)
- BC1. Hierarchy: Platform → Tenant/Organization → Project → Connected Systems/Integrations → Users/Roles
- BC2. Tenant owns: multiple projects, users, roles, billing/subscription associations, tenant-wide policies, tenant-specific data/dashboards
- BC3. Project owns: integrations, timezone, currency, dashboards, alerts, KPI breakdowns, order sources, operational context
- BC4. Integrations scoped at PROJECT level (different system combos per project within same tenant)
- BC5. Users assigned roles at tenant level, project level, or both
- BC6. A single user may have: all-projects-under-tenant access, single-project access, or different roles per project

### BD. Isolation requirements (STRONG verification target — check write/read paths, middleware)
- BD1. Project-level logical data isolation — every major record (orders, customers, sessions, payments, shipments, inventory snapshots, sync jobs, webhook events, KPI records, alerts) carries explicit project + tenant identifiers
- BD2. Project-level filters mandatory in BOTH write and read paths
- BD3. Dashboard components resolve data only for permitted project context
- BD4. Cross-project aggregation only with explicit access
- BD5. Tenant-level authentication isolation — sessions resolve tenant membership; tokens include tenant + role context; tenant/project switch requires explicit scoped access; permission checks before data access/action
- BD6. One tenant's user cannot query/mutate another tenant's resources
- BD7. Scoped connector credentials per project (API keys, OAuth refresh tokens, bearer tokens, service account refs, webhook secrets, SFTP creds, endpoint metadata) — never globally shared
